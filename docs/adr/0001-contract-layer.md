# ADR-0001 — Contract layer: two planes, design-first process with code-first generation

Status: accepted
Date: 2026-08-11
Scope: root — governs `game-server/api-gateway`, `game-client`, and the `game-server/common/api/proto` plane
Realized by: no single FS — adopted per **serialize-on-touch** (slice ⓪ of the first
feature that touches each endpoint's surface). Its blocking precondition is **FS-0001**
(uniform, machine-readable error contract).

## Context

barrowspire has two boundaries where a contract exists whether or not it is governed.

**Plane 1 — `game-client` ↔ `api-gateway` (HTTP).** There is **no spec of any kind** today:
no OpenAPI document, no annotations, no generated client. The gateway's HTTP surface is
defined implicitly by 33+ gin route registrations, and `game-client` hand-writes its calls
against them. A gateway change breaks the client at runtime, in a scene, rather than at build
time. The error surface is worse than undefined — it is **inconsistent**: four different error
body shapes ship today, one of which interpolates a raw downstream error into the response.

**Plane 2 — service ↔ service (gRPC).** `game-server/common/api/proto` already **is** the
contract for the ten downstream services, with committed generated stubs. It has no lint and
no breaking-change gate; a field can be renumbered and nothing objects until a service
misbehaves in an environment.

The deeper force is a process one, not a tooling one. Two things get conflated under the word
"the contract": its **design** (what resources exist, what an operation *means*, what errors
are possible — human judgment, expensive to get wrong) and its **serialization** (the schema
document — mechanical, derivable). Handing both to an agent inverts design-precedes-implementation
at the most expensive boundary in the system. Hand-authoring both produces two artifacts that
drift against each other.

### Alternatives considered and rejected

- **Spec-first** (hand-authored schema → generated server stubs). Two authored artifacts that
  drift, and schema authorship is precisely the mechanical work worth delegating. Correct only
  when the contract **is** the product — a public, third-party API. This one is internal.
- **Pure code-first with no designed table.** The implementer authors the contract and review
  discovers it after the fact — the inversion above, with better tooling.
- **Annotation-based generation.** Comments enforce nothing and drift from the code they
  describe; they are not typechecked against the handler they sit above.
- **Big-bang migration of all 33+ endpoints.** Spends effort protecting endpoints that may
  never change again. Adoption should be triggered by the work, not scheduled ahead of it.

## Decision

**Design-first process, code-first generation** — the two halves are separated and each given
to whoever should own it.

1. **Plane 1 design lives in the feature spec.** The contract's DESIGN is the `§API surface`
   table in each feature's `FS-NNNN` — prose and a table, human-ratified at promotion like
   every other spec section. It pins **shape** (op, method + path, params, request, response,
   errors with `status · code`); semantics stay in Requirements. It is **never** YAML and never
   Go types. Format authority: `docs/specs/README.md`.

2. **Plane 1 serialization is generated, committed, and never hand-edited.**
   `game-server/api-gateway/openapi.yaml` is generated by **Huma v2** from *typed handler
   signatures* — types, not comments, so it cannot drift from the code. It is committed: the
   schema diff **is** the contract review surface on a PR. CI regenerates and **fails on any
   diff** between committed and derived.

3. **Plane 1 gates.** `oasdiff` (pinned, prebuilt binary) against the committed spec detects
   breaking changes — an `ERR` blocks merge; a deliberate break goes through the
   `game-server/.oasdiff-ignore` allowlist, making the break an explicit, reviewable act.
   `Spectral` enforces contract depth: descriptions, examples, and error schemas required.
   Both ship with fixtures (clause 10).

4. **The client consumes only the generated client.** Generated with `openapi-typescript` +
   `openapi-fetch` into `game-client/src/api/generated`. Hand-written fetch against a
   **serialized** endpoint is a **HIGH** code-review finding.

5. **Transport types are declared per operation and are never storage models.** A request type
   carries **writable fields only**: read-only fields (`id`, timestamps) never appear, and
   identity **never** comes from the body — only from the verified JWT or transport metadata.
   This makes a class of mass-assignment bug unrepresentable rather than defended against.

6. **Errors are RFC 9457 `application/problem+json`, with a domain `code`.** The stock problem
   members (`type`, `title`, `status`, `detail`) are extended with:
   - **`code`** — a `SCREAMING_SNAKE` domain error code from `game-server/common/errcode`,
     stable and switchable by client code. **`code` is contract**: removing or repurposing one
     is a breaking change; adding one is not.
   - **`errors[]`** — field-level detail (message, location, value).

   HTTP status stays the coarse routing signal; `code` is the precise one. The client switches
   on `code`, **never** on `detail` — `detail` is prose and explicitly not contract.

   **HTTP error status is decided in exactly one seam.** No handler writes an error status
   directly. This clause is what **FS-0001** builds, and it is a hard precondition for clause 2:
   without one error-mapping boundary, the generated contract cannot describe its own failures.

7. **Validation is two layers with two statuses.** *Shape* — is this a well-formed request for
   this operation? — is decided at the boundary from the type, and fails **422**. *Domain* — is
   it allowed by the domain's rules? — is decided by the **owning downstream service**, and
   fails **400** with a domain code. The gateway never restates a downstream rule, so the two
   cannot drift.

8. **Request strictness follows the deployment model.** Reject unknown input when the consumer
   ships with you; tolerate it when it does not.
   - Plane 1 (`game-client`, same release): **strict** — unknown member → 422. Silently
     ignoring an unknown member turns a client typo into a no-op the user believes succeeded.
   - Plane 2 (independently deployed services): **tolerant** — protobuf ignores unknown fields
     by design, which is the rolling-upgrade property that justifies using it. Its guard is
     `buf breaking` at CI, not runtime rejection.

   **Revisit trigger:** plane 1 strictness is correct only while `game-client` ships with the
   server. The moment a consumer appears that deploys independently, reopen this clause.

9. **Adoption is serialize-on-touch, never big-bang.** An existing endpoint is wrapped —
   behavior-preserving — as **slice ⓪** of the first feature or refactor that touches its
   surface. **No handler rewrite may precede its endpoints' serialization**: the contract is
   established at signature time, before the behavior changes underneath it.

10. **Gate config ships with fixtures.** `game-server/contract-fixtures/` holds known-bad inputs
    the gates must reject, plus a worked allowlist example. A ruleset or allowlist is
    unverified configuration until it has rejected something; a gate that cannot distinguish
    *passed* from *did not run* emits a green check either way, which is worse than no gate
    because it is trusted.

11. **Grandfather clause.** The generated-client-only rule (4) binds **serialized** endpoints.
    Legacy endpoints keep their existing hand-written calls until touched, at which point the
    `game-client` call migrates **within the same feature** — the two halves of one endpoint
    never straddle two features.

12. **Plane 2 is governed by `buf`.** `game-server/common/api/proto` is the contract as-is;
    governance is `buf lint` + `buf breaking` in CI, mapping to the same severities and the
    same `.audit/` destination as plane 1. **Not yet wired** — declared here so the gap is
    explicit rather than silently absent.

**Toolchain pinned:** `huma v2`, `oasdiff@1.28.0` (prebuilt binary, not `go run`),
`@stoplight/spectral-cli@6`, `openapi-typescript@7` + `openapi-fetch`. Pinned means pinned: a
gate running `@latest` can turn red on a day nobody touched the contract.

**Placement note.** The gate configs (`.spectral.yaml`, `.oasdiff-ignore`, `contract-fixtures/`)
live at **`game-server/`**, not the repository root, because that is where `go.work` defines the
Go workspace. Rooting them higher would make the Makefile's relative paths climb out of it.

## Consequences

**Accepted / positive:**

- The expensive half of the contract (design) is decided by a human in the FS *before*
  implementation; the mechanical half (serialization) is derived and cannot drift.
- Generation from **typed signatures** rather than comments removes the drift class entirely —
  the spec is wrong only if the code is wrong.
- `game-client` breaks at `tsc`, not at runtime in a scene.
- Breaking changes become a deliberate, allowlisted act instead of an accident found downstream.
- Migration cost is paid only where work is actually happening.

**Costs / follow-ups:**

- **FS-0001 is a hard prerequisite, not a nicety.** The gateway has ~122 direct error-status
  writes, four error body shapes, and no error package at all. Clause 6's seam must exist
  before any endpoint can be serialized honestly.
- **Huma v2 forces a dependency-floor bump.** The gateway is on `gin v1.11.0` and Go directive
  `1.24.2`; huma v2 requires **gin ≥ 1.12** and **Go ≥ 1.25**. That is a framework-version bump
  across every gin handler in the service, and it belongs in the first serialize-on-touch
  slice's risk note rather than being discovered mid-feature. Verify with
  `go mod graph | grep huma` before slice ⓪.
- **The error body format changes** for wrapped endpoints — a known, deliberate break.
  `game-client` reads `.error` and `.message` across ~15 files; both key names disappear.
  Handled inside FS-0001 rather than left to discovery.
- **Generated artifacts are committed**, so PR diffs get larger. Accepted: that diff is exactly
  what makes the contract reviewable.
- **A transitional period** where serialized and legacy endpoints coexist. Track it with a
  thin-spec line — *Legacy surface serialized → FS-none* — so the remaining migration is
  visible in the capability index rather than in memory.
- **This is barrowspire's first CI workflow.** `.github/workflows/contract.yml` is scoped to
  the contract gates only; build/test CI remains a separate concern.

**Known blind spot — slice ⓪ is not covered by the ratchet:**

> On **wrap slices**, before/after behavior verification is **manual**; the oasdiff ratchet
> guards only from first merge onward.

The breaking-change gate compares the schema document against its own previous revision. An
endpoint's *first* serialization has no previous revision — and its breaks are relative to
whatever described the endpoint before, which here is **nothing at all**. Those breaks are
invisible to plane-1 detection by construction.

This is not a defect to fix; it is a property to staff. Slice ⓪ is verified by review and by the
before/after behavioural checks written into its FS. Expect the gate to report
`SKIPPED: no baseline` until the first merge, and read that as correct rather than broken.

**Also unproven at adoption time, by construction:** the regenerate-and-diff gate, the
breaking-change gate, and the client-staleness check cannot be *proven* until this repo's first
serialized endpoint exists. The fixtures in clause 10 are what make the gates verifiable before
then — run them now, not later.
